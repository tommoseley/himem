HiMem · Architecture

Architectural Invariants

Everything else depends on these. Every design must express them — it may not quietly redesign around them. To change one, raise it as an explicit challenge to the architecture, and leave it in force until it's ruled on.

The architecture is optimized for understanding, not organization — HiMem helps people build meaning, not file information.

Ontology

  • Clip = evidence — the atomic unit of HiMem; everything else is built by referencing clips
  • Memory = context — an interpretation formed over one or more referenced clips, plus a derived layer (title · summary · topics)
  • Project = intent — a long-running effort around a name and a goal
  • Clip ↔ Memory is many-to-many · Memory ↔ Project is many-to-many
  • Session = a grouping of captured clips awaiting review — it need not become a memory
  • Audio is the source of truth — transcripts are derivative, regeneratable

First principles

  • Memories are perishable — never make the user carry one while navigating
  • Capture is one action from anywhere — defer every decision but "record now"
  • Capture once, connect many — one clip can be evidence in many memories
  • No user content in HiMem's custody — it lives in the user's own iCloud
  • Watch clips ship compressed — mono · 16 kHz · AAC before transfer, never raw PCM; an encoding fix, not a transport change (guard: the file handed to transferFile is mono/16k/AAC — that test failing is the bug)

Interaction

  • Surfaces create their own objects — the + is context-aware to the tab
  • No magic navigation — capture stays where you are; nothing teleports
  • Capture now, decide later — structure forms on reflection, never at the catch
  • One surface per concept — modes (view ↔ edit), not extra screens
  • Tap the active tab → status sheet — what needs me, not how much I have

AI

  • AI observes, never concludes — describe, don't interpret (Honest Label)
  • Under-suggest — a confident wrong proposal is worse than none
  • AI is blue, always — never ochre or amber
  • Named actions, trailing ✦ — "Organize with AI," "Find the thread"; never "Regenerate"
  • The draft is editable, never authoritative — Free on tap, Plus automatically

Navigation

  • Three tabs: Clips • Memories • Projects = Evidence · Context · Intent
  • Memories is the reflective home surface — what you open HiMem for; cold launch lands here
  • Clips is the operational evidence surface, first-class — the standalone Captured Clips window is retired
  • Projects is the intent surface — long-running efforts, entered deliberately

Affordances

  • Colour maps to who acts — ochre = you · blue = AI · red = destruction
  • Three signals, one meaning each — real button · managed pill · quiet label
  • Delete = one button, bottom of an opened item — no confirm; swipe-to-delete retired
  • 44px hit-target floor · toggle on-state ochre (never green) · status never colour alone

Clips surface

  • Two filter axes — New ⟷ All (status) · All / Voice / Photos / Video / Notes (type)
  • Source-agnostic copy — "N new clips," never "from your Watch"
  • The list is calm — Create / Delete live inside the opened session
  • Start a Memory — connects the session's clips to a new memory (which shows them at once) · confirm · session consumed · connected clips no longer appear in New

Voice

  • Quiet over loud · specific over clever · warm over neutral
  • Plain English — no jargon, no emoji
  • Never blame the user — "We couldn't reach…," never "You are offline"

The review rule

Does this express the architecture?
— asked first, before "Is there a better design?"

Two classes of edit. A coherence fix may be applied freely when it reconciles two existing invariants without changing either one — making the words stop contradicting the model (e.g. "contains" → "connects"). A vocabulary, architectural, or principle change alters an invariant itself and requires explicit approval — raise it as a challenge and leave the invariant in force until it's ruled on.

The ontology changes rarely; the mechanics evolve continuously. Architecture is optimized for stability, mechanics through dogfooding — don't reopen the ontology because a mechanic feels awkward. Fix the mechanic first.
