Notes

Mechanics behind the visible behavior.

Typed scopes

Three scopes ship in v1: topic:, type:, date:. Typed scopes are discoverable through the Filter-by suggestion list — the user doesn't need to know the syntax to use it.

  • topic: garden, cooking, work, etc.
  • type: voice, text, photo, video
  • date: today, this-week, last-month, 2024, before:apr-1

Scopes compose: topic:garden type:voice tomato works.

Chips vs typed

Below the search field, scope chips appear only after results render — they're a faceted filter on the current result set, not a pre-filter on what to search.

They reflect the actual distribution of results (counts shown). Tapping Garden narrows; tapping All widens.

Power users skip the chips entirely and type scopes inline. Both paths produce the same query.

Highlighting

Matched terms get a warm-yellow highlight (rgba(255,213,110,.55)) — not the accent ochre. Two reasons:

  • Ochre is reserved for primary actions and brand. If we use it for highlights, it loses meaning.
  • Yellow reads as "marker" universally. Lower cognitive cost.

The "Forgotten" card

Pre-search shows one randomly surfaced entry from the deep Memory Box (older than 6 months, not opened in >3 months). Italic serif quote, topic pip, age.

This is the only place HiMem surfaces randomness. It's not gamification — it's the Memory Box doing what a Memory Box does: surprising you with something you forgot you had.

Date sectioning

Results are grouped by relative buckets, in this order:

  • Today / Yesterday (if any match)
  • This week
  • Last month (Mar / Feb / Jan…)
  • Earlier in YYYY
  • Older

Ordering within a bucket: relevance first, then recency.

Why no separate filter sheet

A filter funnel icon → modal sheet was the alternative. We rejected it because:

  • It hides scope behind a tap. Users forget it exists.
  • Scope chips + typed scopes cover 95% of intent with zero modal weight.
  • If we ever need date-range pickers or "edited only" toggles, we add a small More filters chip — not a sheet.

One field, three powers

Free text. Typed scopes. Scope chips. Same field, three escalating levels of precision. The user doesn't have to choose which one they're using.

Always a way forward

No-results is a screen of intent, never a dead end. Capture is the hero action — visually primary, full ochre, framed as transformation. The query you couldn't find becomes the memory you're about to make. Broaden and browse stay below as quieter fallbacks.

Search is memory-adjacent

What you searched for can be more revealing than what you saved. So: local-first, never synced by default, no analytics on raw terms. Per-item dismissal, "Forget all" for the whole list, and a future Private search mode that doesn't write history at all. Voice queries follow the same rule — on-device transcription via Apple's Speech framework where possible, never raw analytics, treated as the same sacred history.

One intent, four entry points

HiMem exposes a single Search Memory Box App Intent. Siri, Shortcuts, and Spotlight all route through it. "Hey Siri, search HiMem for tomato trellis" lands on the same results as the in-app voice flow. One pipe, many openings — the experience stays HiMem's, the plumbing is Apple's.

Confirm before you run

Voice search shows what HiMem heard and what it inferred before firing results. v1 default: always confirm. Later, a setting (Search immediately after voice input) can let confident queries skip the interpreted step. The product should learn — but on the user's terms, not by default.

Performance budget

Every keystroke debounces at 120ms. Results render under 200ms for <1k entries (local index). For larger Memory Boxes, we show a skeleton row at 250ms and stream results in.
