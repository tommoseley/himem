## Implemented — 4× duplicate clip delivery (`fef4ba0`)

- Observed: one 21 s clip arrived four times from four distinct WC transfer directories, each a full re-transfer; `tombstones=10`.
- Root cause: every `flushPendingManifest` trigger re-entered `send` → `enqueueReadyTransfer`, whose only de-dup gate was `outstandingFileTransfers` — which holds only *incomplete* transfers, while the manifest row survives until the iPhone acks. Between "delivered" and "acked" the clip looked un-sent.
- The code comment asserted the guarantee that did not exist ("`transferFile` de-dupes in-flight transfers, so this is safe to fire on any reachability change"). Replaced.
- Fix: pure `nonisolated shouldEnqueue(clipId:outstanding:deliveredAwaitingAck:)` (mirrors `WaveformLevelThrottle.observe`); `deliveredAwaitingAck: [UUID: UUID?]` populated on `didFinish` success; cleared on clip ack (both wire formats), rollGroup ack (every member), and `activationDidCompleteWith`.
- Activation-clear is what makes suppression safe: a reinstalled phone presents a new WC identity, so a clip stranded by a reinstall is re-shipped by the event that stranded it.
- rollGroupId carried in the delivered-set rather than looked up in the manifest at ack time — a lookup would depend on running before the coordinator prunes rows (ordering coincidence, not invariant).
- 6 money tests. Red verified first: `(decision → true) == false`.

## Implemented — data-loss delete + orphan reclaim (`10b49fb`)

- Presented as a 30-second transcription delay; was a **data-loss path**. Symptom and defect had different owners.
- Every delivery copies to the same canonical path and the copy is idempotent, so there is never a redundant file. Both redelivery-rejection branches nonetheless did `removeItem(at: masterURL)` to "drop the redelivered master file so disk doesn't bloat" — a false premise, so the delete could only destroy the **live audio of the already-accepted clip**.
- Observed sequence: delivery #2 deleted the master → `kAudio_FileNotFoundError` → recovered only because delivery #4 re-copied the bytes. Had that been the last delivery, the recording was gone (storage lock: audio is source of truth).
- The duplicate-delivery fix removes the *trigger* but not the bug — it would have gone quiet while staying live.
- Both unconditional deletes removed; post-split consume retained (there the master genuinely lives on in the fragments).
- Narrower regression introduced and then fixed in the same commit: a split clip's redelivered master is unreferenced and `MediaBlobOrphanSweep` is unwired, so nothing reclaimed it. Added `shouldReclaimRedeliveredMaster(masterFilename:referencedFilenames:)` — referenced ⇒ keep, unreferenced ⇒ reclaim via `UbiquityStore.removeFromStore` (coordinator-wrapped, per RH-8). Deliberately not applied to the `tryEnter` branch (another task is mid-processing).
- Money tests both directions, each red-verified first.
