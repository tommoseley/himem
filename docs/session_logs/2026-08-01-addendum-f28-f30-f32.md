## NEW: exit 73 is out of disk — and it revises this morning's simulator ruling

**`xcodebuild` exits 73 on `ENOSPC`.** Signature: 0 compile errors, **no result bundle**, and a filesystem error in the tail rather than anything about tests. In a scripted loop it reads as a failed gate. It is the **fourth distinct exit code** this project has had to learn to read, and the first about neither the build nor the simulator.

The cause is **cumulative**, which is why it arrives late in a long session and looks sudden:

- every paired gate writes a `.xcresult` (~10 MB) — the scratchpad reached **141 MB** (now 7 MB);
- DerivedData grows;
- **erasing** simulators rather than deleting them keeps their data.

Once the volume fills, **every subsequent command fails, including the ones that would clear space** — the session could not recover without freeing disk externally.

**This revises the 07-31 ruling "erasing is the standing answer" into something more precise:**

> **`simctl delete` for spent devices, `erase` only for one being kept. Delete result bundles between runs.**

Recorded in `CLAUDE.md` § Measurement Discipline (`40a9900`).

## The work

### F28 · Learn survived a tab round-trip (`18c0caf`)

**Root cause is an OWNERSHIP error, not a lifecycle one.** `showTutorials` was tab-local `@State`, and Learn **pushes** onto that tab's own `NavigationStack`. A `TabView` keeps every tab alive, so nothing ever popped it: the tab stopped being visible and came back with its stack exactly as left. **A tab cannot observe that the tab changed; the shell can.**

Ownership moved to `HiMemTabView.learnOpenOn`, cleared in the shell's existing `.onChange(of: selection)`.

Two shape decisions, both load-bearing:

- **`Tab?`, not a shared `Bool`.** One flag would have pushed Learn onto all three stacks at once — a subtler bug than the one being fixed.
- **NOT a fourth ambient singleton.** The obvious move was another shared context beside `ProjectsNavigationContext` / `MemoryDetailPresentationContext` / `ClipDetailPresentationContext`. That accumulation is precisely the bill **F6** names ("every one of those globals was a locally reasonable call"). The shell already owns tab selection, so it is the honest owner.

**Deliberately NOT fixed via `.onDisappear`.** Whether `TabView` fires it reliably is exactly the class of semantics **F25** established should not be built on — there, deciding at tap time rather than chasing `.sheet`/`onDisappear` behaviour is what made one fix cover three paths.

### F30 · Attach ran several silent seconds on a frozen picker (`8968129`)

`PhotoLibraryPicker.picker(_:didFinishPicking:)` copies **every** picked item into the ubiquity container before it calls back, and `PHPickerViewController` **does not dismiss itself**. So the window between her tap and the callback is a multi-second freeze on a picker that looks finished — real work with no signal, which reads as both a hang and a no-op.

The picker now reports progress **outward** (`importingCount`); the owner draws the indicator over the sheet. **Nothing is pushed into the live picker** — `CLAUDE.md` § "UIKit Pickers in SwiftUI" is explicit that doing so tears down its session, and that rule exists because it already cost a black preview once. `updateUIViewController` stays empty. Progress is announced **before** the task starts, since the gap between tap and first observable thing *was* the defect.

### F32 · The creation toast, generalized (`b9d623a`)

`MemoryCreatedToast` → **`CreationToast`** with three kinds — **Memory created · Clip saved · Project created** — and the **whole toast** is the tap target rather than just the trailing link. Styling and duration unchanged; the only behavioural addition is the tap region.

Guards encode the rules, not the pixels: the copy names the **object** (three kinds asserted **distinct**, same reason "not yet transcribed" and "transcribed to silence" must not share a string — F24 D4); the toast may not reference `pendingOpenMemoryId` / `NavigationLink` / `onAppear` (**never auto-navigates**); no nested button may steal the row's taps (the F29 shape one layer up).

**SCOPE LIMIT, STATED NOT IMPLIED:** the component is generalized and the **memory** call site is wired. **Clip-saved and project-created are NOT wired** — there is no creation signal at those moments equivalent to `MemoryNavigationBus.justCreatedMemoryId`, and minting two buses exceeds what this item's ruling covered. The kinds exist, are tested, and are ready; **the wiring is the remaining half.**

## THE RING RULING (F32's design question, answered and ruled)

**Question:** can the walkthrough ring be retired now that the toast exists?

**The load-bearing distinction:** the toast is **rendered by the code path that did the creating**, so it *cannot miss its moment*. The ring has to **predict when she will look**. That is why both prior ring fixes were patches to a prediction problem rather than solutions to it — a window that closed before she looked (**F20a**), an `onAppear` that had already fired (**F20b**).

**But they do different jobs, and only one is redundant:**

| | Question answered | Asked when |
|---|---|---|
| **Toast** | *"Where did it go?"* | at creation, on the surface she's already on |
| **Ring** | *"Which one of these is mine?"* | later, in a list of many |

`memoryInList` exists precisely because she can reach the Memories list **without** tapping the toast — at which point the toast is gone and her row is one of N.

**RULED (2026-08-01), in this sequence:**

1. **Retire the ring's creation-confirmation role.** The toast owns that outright.
2. **Keep the ring as the list-disambiguation anchor** — what F16 originally built it as: the target identifying itself when the referent is one of a set.
3. **Sequence:** wire clip-saved and project-created toasts → then narrow the ring → and only consider full retirement once something anchors a **clip on the bench**.

**THE CAVEAT STANDS, AND IT BLOCKS FULL RETIREMENT:** retiring the ring entirely would leave walkthrough **step 2** — *"Saved. Here it is."* — pointing at nothing, because **no bench clip ever wears a ring**; the ring exists only for memory rows. That is **F16's unclosed half (B)**, which F26 did not fix and which remains live.
