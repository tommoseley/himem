### Troika 3-reviewer audit + 5 fixes (`0037e90`)
Three parallel general-purpose agents reviewed the audio pipeline under distinct lenses. All three converged on real bugs that COMPOUNDED. This was the multi-day mystery finally cracked.

**The three findings:**

1. **Reviewer 3 (end-to-end integrity):** watch's `AVAudioInputNode` was running **Voice-Processing I/O**. In VPIO output, channel 0 is the **downlink reference channel** (silence when nothing is playing); the mic is on a later channel. My `channelMap = [0]` had been extracting silence every retry. Cited to Apple forum thread 710151.
2. **Reviewer 2 (SpeechAnalyzer input requirements):** `TranscriptionService` was **guessing** the target format (hardcoded `Float32`) instead of asking `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)`. And it never called `prepareToAnalyze(in:)` — the sibling `SpeechService.swift` class doc literally says: *"Without it, start returns immediately instead of waiting for the input stream to finish."* That matches the 0-segment, 0-coverage, `[DIAG=rejected]` signature EXACTLY.
3. **Reviewer 1 (AVAudioConverter API correctness):** the block-based transcode loop with per-block `didConsume/noDataNow` starves the resampler's internal filter — the exact bug I reverted from the watch tap that same evening, then shipped again in the transcribe path. Reviewer 1 caught me quoting my own reverted comment.

**Five fixes landed:**

- **#1 (WatchRecordingService):** `inputNode.setVoiceProcessingEnabled(false)` before grabbing `recordingFormat`. Root cause fix — kills the whole channel-map problem at capture. Future recordings are mono.
- **#2 (TranscriptionService):** ported the working `SpeechService` pattern — `bestAvailableAudioFormat` → cache the negotiated format → transcode to whatever it returned → `prepareToAnalyze(in:)` → `start`. Removed the dead `recognizerTargetFormat` constant, `isRecognizerCompatibleFormat` predicate, old `transcodeToRecognizerFormat`.
- **#3 (TranscriptionService):** rewrote transcode as a **single `convert()` call with stateful input block** that reads chunks from the source file continuously and signals `.endOfStream` at EOF. Resampler filter state preserved across the whole file. Dropped `channelMap = [0]` — default AVAudioConverter downmix (average across channels) is safer than picking one blind.
- **#4 (WatchSessionDelegate.compressIfPossible):** elevated the compressor's silent-failure log to `[HiMem][WC][Compress][FAIL]` with the source format captured. Reviewer 3 flagged that AudioCompressor was likely failing silently on multi-channel VPIO input, leaving raw 10 MB PCM on disk instead of ~300 KB AAC.
- **#5 (WatchSessionDelegate.probeChannelEnergy):** per-channel RMS + peak amplitude probe on arrival for every clip. Speech reads ~0.01–0.1 RMS, silence near zero. Turns "which channel has the mic" from guess into measurement. Diagnostic — keep for one TF round; strip if pipeline stabilizes.

Also added a transcoded-output peak-amplitude log line — if the transcode succeeds but produces silence, this catches it in one line.

Existing 8 `TranscriptionPipelineOutcomeTests` pass including the fixture-based real-transcription test. Full iPhone suite: 698 tests, 83 suites.

## Risks

- **The transcode rewrite is untested end-to-end** on a fresh watch recording. Existing fixture-based test uses a mono-16k fixture that doesn't exercise the multi-channel-downmix or the resampler-continuity path. Only real-device dogfood verifies both.
- **Setting `voiceProcessingEnabled = false` on the watch** collapses the input to mono but may change perceived audio characteristics — no noise cancellation, no echo suppression. For a journal recorder this is desirable per Troika reviewer 3, but users used to phone-call-quality noise reduction may notice.
- **The AVAudioConverter single-`convert()` pattern** is untested for very long files (>5 min). The output buffer allocation is pre-sized to `expectedFrames + 4096`; for a 5-min mono 16 kHz recording that's ~4.8 M frames × 4 bytes = 19 MB. Fine but worth monitoring.
- **The channel-RMS probe** reads up to 5 seconds of the file and iterates every sample — cheap for typical clips but visible on long ones. Guard with a sample cap if it shows in profiling.
